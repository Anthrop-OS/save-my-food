# 产品需求文档 (PRD): 感官DNA (Sensory DNA)

* **功能名称:** 感官DNA (Sensory DNA)
* **内部代号/Schema:** `Component Sensory Profile v3.0`
* **版本:** 1.0

## 1. 概述与愿景 (Overview & Vision)

### 1.1 问题陈述 (The Problem)

对于我们的核心用户（特别是AuDHD/ND人群，以及任何处于认知负荷下的个体），食物的**不可预测性**是一个巨大的、未被解决的焦虑来源。现有的营养或食谱APP将食物视为静态的数据点（卡路里、食谱步骤），完全忽略了其动态的、充满细微差别的感官体验。

这种忽略导致了具体的痛点：

* **感官焦虑:** “这个牛油果是‘好’的奶油状，还是‘坏’的纤维状？如果口感不对，我今天可能就吃不下饭了。”
* **执行瘫痪:** “我的生菜看起来有点蔫，它还能吃吗？这种不确定性让我不想去碰它，最后导致食物浪费和点外卖。”
* **信任缺失:** 用户无法信任APP的推荐，因为APP不理解他们个人化的、充满语境的感官世界。

### 1.2 我们的解决方案 (The Solution)

**感官DNA (Sensory DNA)** 是一个革命性的功能，它将食物从一个“黑盒子”转变为一个**完全透明的、可预测的、动态的感官实体**。

它不是一个简单的标签系统，而是一个**智慧的、充满语境的感官分析引擎**。它为每个食物组件建立一个深刻的“感官档案”，能够描述、预测并解释其随时间变化的口感、呈味和香气。

### 1.3 愿景 (Vision)

通过“感官DNA”，我们的平台将成为第一个**真正理解食物“感觉如何”**的营养系统。我们将把用户的感官安全置于产品设计的核心，将我们的平台从一个“数据工具”提升为一个**用户可以完全信赖的“外部感官伙伴”**
，从而建立无与伦比的用户信任和忠诚度。

## 2. 用户画像与用户故事 (User Personas & Stories)

### 2.1 核心用户

* **亚历克斯 (AuDHD优化者):** 30岁，自由职业者。对食物的质地和味道极其敏感，微小的不可预测性都可能导致其一整天饮食计划的崩溃。渴望通过结构和数据来减少生活中的不确定性。
* **本 (NT效率追求者):** 40岁，有两个孩子的职场父母。时间极其宝贵，认知负荷常年处于高位。讨厌浪费食物，但经常因为太累而无法处理冰箱里的食材。

### 2.2 用户故事

* **作为亚历克斯，** 我希望在我选择一个食材时，就能**精确地知道**它“现在”的口感和味道是怎样的，这样我才能避免触发我的感官厌恶，并感到安全。
* **作为亚历克斯，** 我希望系统能**主动提醒**我，某个食材的感官体验即将发生负面变化，并告诉我该如何处理，这样我就不必每天都去检查和焦虑。
* **作为本，** 我希望系统能**清晰地告诉我**冰箱里的生菜是还能做沙拉，还是已经只适合炒菜了，这样我就可以快速做出决定，而不是把它放烂。
* **作为本，** 我希望在我使用“一键拯救冰箱”功能时，系统能**智能地**根据食材的“当前状态”提出最合适的食谱，而不是给出一个不切实际的建议。

## 3. 功能需求 (Functional Requirements)

### 3.1 FR1: 感官DNA档案库 (The Sensory DNA Library)

* **3.1.1:** 系统后端必须能够加载、解析并存储基于 `Component Sensory Profile v3.0` Schema 定义的YAML文件。
* **3.1.2:** 每个组件必须有一个可访问的详情页，用于展示其“感官DNA”。
* **3.1.3:** 系统必须支持Schema中定义的所有核心对象：`State` (状态), `Attribute` (属性), 和 `Transition` (转换)。

### 3.2 FR2: 感官DNA可视化界面 (The Sensory DNA UI)

* **3.2.1:** 在组件详情页，必须以清晰、可视化的方式展示其**当前状态**的`sensory_attributes` (感官属性)。
* **3.2.2:** 属性的展示必须使用**颜色编码**来区分其`valence` (价值/效价)：
    * `positive`: 绿色
    * `neutral`: 灰色
    * `negative`: 橙色/红色
* **3.2.3:** UI必须能清晰地展示一个属性的`tag_id` (来自词典的名称)、`source` (来源) 和`intensity` (强度)。
* **3.2.4:** 对于有状态转换的组件，UI必须提供一个入口，允许用户查看其完整的“生命周期”和不同状态下的感官档案。

### 3.3 FR3: 动态状态机与通知系统 (The Dynamic State Machine & Notification System)

* **3.3.1:** 当用户在其“库存”中添加一个有生命周期的组件时，系统必须在后台为其启动一个**内部计时器**。
* **3.3.2:** 当一个组件的计时器到达其`lifespan_days`的阈值时，系统必须自动将其状态更新为下一个状态（例如，从`optimal`更新为`degraded`）。
* **3.3.3:** 当状态发生负面转换时，系统必须向用户发送一个**主动的、非侵入性的推送通知**，通知内容应使用`Transition`对象中定义的`user_alert`文本。
* **3.3.4:** 用户必须可以在设置中控制这些通知的频率和开关。

### 3.4 FR4: 与核心功能的深度集成 (Deep Integration with Core Features)

* **3.4.1 (为您起草):** “为您起草”功能在生成草案时，**必须**优先考虑组件的**当前感官状态**。它应优先使用即将或已经`degraded`的组件，并在解释中说明原因。
* **3.4.2 (拯救冰箱):** “一键拯救冰箱”功能**必须**使用组件的当前感官状态来提出更精准的食谱建议（例如，`degraded`的生菜推荐用于炒菜而非沙拉）。
* **3.4.3 (筛选与搜索):** 用户**必须**能够基于感官属性（包括`tag_id`, `valence`, `intensity`）来筛选和搜索`组件库`。

## 4. 技术与数据考量 (Technical & Data Considerations)

* **数据源:** 核心的感官档案数据将由内部的营养学和食品科学团队在`component_sensory_profiles.yaml`文件中进行定义和维护。该文件是系统的“宪法”。
* **后端逻辑:** 需要一个健壮的后台任务处理器（如Celery, Sidekiq）来管理成千上万个组件实例的独立计时器和状态转换。
* **前端框架:** 建议使用能够高效处理动态数据绑定和条件渲染的前端框架（如React, Vue）来构建“感官DNA”的可视化界面。

## 5. 衡量成功的指标 (Success Metrics)

* **功能采纳率 (Adoption):** 查看“感官DNA”详情页的月活跃用户比例 > 30%。
* **用户参与度 (Engagement):** 用户对“感官状态变化”通知的打开率和后续操作率（例如，将被提醒的组件加入计划）。
* **任务成功率 (Task Success):** 启用“感官DNA”的用户，其“一键拯救冰箱”功能的使用频率和满意度得分更高。
* **用户留存率 (Retention):** 深度使用“感官DNA”功能的用户，其长期（3个月后）留存率显著高于平均水平。
* **定性反馈 (Qualitative):** 通过用户访谈，收集到诸如“这个功能让我感到安全”、“它减少了我的食物焦虑”等正面反馈。

## 6. 未来迭代方向 (Future Iterations - Out of Scope for V1)

* **V1.1: 用户反馈循环:** 允许用户对自己库存中组件的“实际感官状态”进行反馈，以微调我们的计时器模型。
* **V1.2: 图像识别辅助:** 在“拯救冰箱”功能中，使用图像识别初步判断食材的新鲜度，作为状态预测的辅助输入。
* **V2.0: 用户自定义档案:** 允许高级用户创建或自定义他们自己的`Component Sensory Profile`。
