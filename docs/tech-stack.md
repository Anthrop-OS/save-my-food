## 1. 核心哲学：我们的技术如何服务于产品愿景

本项目的核心使命是为用户（特别是AuDHD/ND人群）提供一个**认知无障碍、充满同理心的外部认知伙伴**。我们的技术栈不是为了追逐潮流，而是为了在工程层面**严格践行**这一核心哲学。

我们的技术选择遵循三大原则：

1. **认知无障碍 (Cognitive Accessibility):** 我们选择能降低开发者认知负荷、消除模糊性、提供清晰结构的工具。一个让开发者感到轻松的系统，才能最终构建出一个让用户感到轻松的产品。
2. **单一事实来源 (Single Source of Truth):
   ** 我们致力于消除重复和不同步。无论是类型定义、设计规范还是核心逻辑，都必须存在于一个单一的、权威的位置。
3. **低摩擦的迭代 (Low-Friction Iteration):** 我们选择能让我们快速、安全地响应用户反馈的工具，确保产品能够持续进化。

## 2. 宏观架构 (High-Level Architecture)

我们将采用 **Monorepo（单一代码库）** 架构来管理整个项目。

* **核心优势:** 完美践行“单一事实来源”原则，允许前后端及共享包之间的无缝代码共享与原子化变更。
* **工具:** 使用 **pnpm Workspaces** 进行包管理，**Turborepo** 进行任务编排与构建缓存，以实现极致的开发与CI/CD效率。

### 项目结构概览:

```
/
├── apps/
│   ├── api/          # 后端: NestJS 应用
│   └── web/          # 前端: Next.js 应用
├── packages/
│   ├── core/         # 核心业务逻辑与YAML解析器
│   ├── dto/          # 共享的DTO (使用Zod定义)
│   ├── ui/           # 共享的React UI组件库 (基于Radix + Tailwind)
│   └── config/       # 共享的ESLint, Prettier, TSConfig等配置
└── ...
```

## 3. 面向软件开发工程师 (SDE) 的技术栈详解

### 3.1 跨端通信与数据契约

* **语言:** **TypeScript (Strict Mode)**
    * **要求:** 整个代码库必须启用严格模式。**类型安全是我们认知无障碍的第一道防线。**
* **DTO共享:** 使用 **Zod**
    * **工作流:** 在 `packages/dto` 中使用 Zod Schema 作为“单一事实来源”。后端使用它进行**运行时验证**，前端通过 `z.infer<>` 获得**编译时类型安全**。
    * **禁止:** 任何手写的、重复的类型定义。

### 3.2 后端 (Backend)

* **框架:** **NestJS**
    * **理由:** 提供了一个健壮的、模块化的、面向对象的架构，非常适合构建可维护、可扩展的API。其依赖注入系统和装饰器使得代码结构清晰。
    * **最佳实践:** 充分利用其模块(Modules)、服务(Services)和控制器(Controllers)的分层结构。
* **数据库:** **PostgreSQL**
    * **理由:** 世界上最先进的开源关系型数据库。其强大的JSONB支持、稳定性和可扩展性，非常适合我们存储复杂的`Component Sensory Profile`数据。
    * **ORM:** 使用 **Prisma** 或 **TypeORM** 来与数据库交互，确保类型安全。
* **部署:** **AWS**
    * **服务:** 使用 **ECS/Fargate** 运行容器化的NestJS应用，**RDS** for PostgreSQL，**S3** for 文件存储，通过 **Infrastructure as Code (IaC)** (如 Terraform 或 AWS CDK) 进行管理。

### 3.3 前端 (Frontend)

* **框架:** **Next.js (App Router)**
    * **理由:** 强大的React框架，提供服务器端组件(RSC)、智能路由和优化的性能。
    * **最佳实践:** 善用服务器端组件来获取数据，减少客户端的负担。
* **状态管理:** **Zustand**
    * **理由:** 极其简单的全局状态管理方案，API直观，认知负荷低，完美契合我们的哲学。
    * **禁止:** 过度使用全局状态。优先考虑组件本地状态和URL状态。
* **数据请求/缓存:** **TanStack Query (React Query)**
    * **要求:** **所有**与后端API的通信都必须通过 TanStack Query 进行。
    * **理由:** 它自动处理缓存、后台同步、重试和乐观更新，极大地简化了服务器状态管理，让UI感觉更“活”。
* **测试:**
    * **单元/集成:** **Vitest** + **React Testing Library (RTL)**。我们测试用户的行为，而不是组件的内部实现。
    * **端到端:** **Playwright**。每个核心用户故事都必须有对应的Playwright测试，并且**必须开启其无障碍检查 (Accessibility Checks)**。

## 4. 面向设计师 (Designer) 的技术栈与协作指南

设计师是我们“认知无障碍”理念的守护者。以下技术栈的选择，旨在最大限度地**赋能设计师的创造力**，并确保设计稿能够被**像素级、无障碍地**实现。

### 4.1 核心设计系统 (Core Design System)

* **UI组件基础:** **Radix UI**
    * **对设计师的意义:** 这是我们的“**无障碍骨架**”。设计师在Figma中设计组件时，无需从零开始考虑所有ARIA属性和键盘交互。我们可以确信，只要工程师使用了对应的Radix原语，组件的底层无障碍性就得到了保证。
* **样式:** **Tailwind CSS**
    * **协作方式:** 设计系统必须在Figma中**以Tailwind的配置为“单一事实来源”**。这意味着，Figma中的**颜色、间距、字体大小、阴影**等设计令牌 (Design Tokens)，其命名和值必须与我们项目中的`tailwind.config.js`文件
      **完全同步**。
    * **优势:** 这消除了“设计师用8px，工程师用10px”的混乱。工程师可以直接将Figma中的设计，用Tailwind的类名 (`p-2`, `text-lg`, `shadow-md`) 精确地翻译为代码。

### 4.2 交互与动效 (Interaction & Motion)

* **拖放交互:** **dnd-kit**
    * **设计师的角色:** 设计师需要为我们的“Stacklands”式卡牌交互，设计清晰的视觉状态：`拖拽中`、`可放置区域`、`放置成功/失败`。dnd-kit能够完美实现这些，并且是无障碍的。
* **动画:** **Framer Motion**
    * **设计原则:** 我们的动画哲学是“**有意义，而非炫技**”。动画的目的是：
        1. **引导注意力 (Guide Attention):** 温和地高亮重要信息。
        2. **提供反馈 (Provide Feedback):** 确认用户的操作已成功。
        3. **平滑过渡 (Smooth Transitions):** 减少界面状态变化带来的突兀感。
    * **协作方式:** 设计师可以使用Framer的动效设计工具，工程师可以轻松地将这些参数（如`duration`, `easing`)转化为Framer Motion的代码。

### 4.3 设计师与工程师的契约

* **共享UI库:** 我们将在Monorepo的 `packages/ui` 中，共同构建一个**共享的、可复用的React组件库**。
* **Storybook:** 我们将使用 **Storybook** 来为这个UI库创建文档和交互式沙盒。
    * **设计师的工作流:** 在设计新功能前，首先检查Storybook中是否已有可用组件。
    * **工程师的工作流:** 开发新组件时，必须为其编写Storybook文档，并包含所有设计中定义的状态 (variants)。
* **Figma -> Storybook -> App:** 这是我们UI开发的“单一流向”。Storybook是我们设计与工程之间**共同的、可交互的“单一事实来源”**。

这是一个顶级的、展现了资深工程领导力的提问。选择一个技术栈仅仅是第一步，**理解并记录下选择每个技术时我们所做的“权衡” (Trade-offs) 和“考量” (Considerations)，才是确保团队能够在未来做出明智决策、避免技术债、并保持架构一致性的关键。

# 技术栈考量与权衡 (Tech Stack Considerations & Trade-offs)

* **版本:** 1.0
* **目的:** 本文档记录了我们为 [项目代号] 选择核心技术栈时的关键考量、我们接受的权衡，以及我们为缓解这些权衡所制定的策略。

## A. 宏观架构 (Architecture)

### **Monorepo (via pnpm + Turborepo)**

* **核心考量 (Why we chose it):**
    * **单一事实来源:** 完美支持跨端共享 `dto`, `types`, 和核心逻辑，是我们架构哲学的基石。
    * **原子化变更:** 极大地简化了涉及前后端的全栈功能的开发、审查和部署。
    * **开发效率:** `Turborepo` 的缓存机制能显著加速CI/CD和本地构建，`pnpm` 则高效管理依赖。
* **我们接受的权衡 (The Trade-offs we accept):**
    * **初始设置复杂性:** 相比于多个独立仓库，搭建一个健壮的Monorepo需要更多前期配置（TypeScript路径别名, CI缓存策略等）。
    * **工具链耦合:** 团队成员需要学习并依赖Monorepo的管理工具（`pnpm`, `Turborepo`）。
* **缓解策略 (Our Mitigation Strategy):**
    * 我们将投资编写一份详尽的 **`CONTRIBUTING.md`** 和**入职文档**，清晰地指导新成员如何设置和使用这个环境。
    * CI/CD流水线将由核心架构团队统一维护，对普通开发者透明。

## B. 后端 (Backend)

### **NestJS**

* **核心考量:**
    * **结构与规范:** 其“约定优于配置”和模块化的架构，为构建大型、可维护的应用提供了极佳的脚手架，能有效避免项目陷入混乱。
    * **TypeScript原生:** 装饰器和依赖注入系统与TypeScript深度集成，提供了卓越的开发体验和类型安全。
* **我们接受的权衡:**
    * **学习曲线:** 对于习惯了纯Express.js等轻量级框架的开发者，NestJS的“重量级”概念（Modules, Providers, Decorators）有一定学习成本。
    * **代码冗余 (Boilerplate):** 相比轻量级框架，实现一个简单的CRUD端点可能需要创建更多的文件（Module, Controller, Service）。
* **缓解策略:**
    * 我们将利用NestJS的**CLI工具**来自动生成模块、服务等模板代码，以减少手动编写的冗余。
    * 团队内部将定期举行分享会，共同学习NestJS的最佳实践。

### **PostgreSQL + Prisma**

* **核心考量:**
    * **数据完整性与强大功能 (Postgres):** 关系型数据库的ACID特性是数据可靠性的保证。Postgres的JSONB支持也为我们灵活存储`Sensory Profile`等半结构化数据提供了便利。
    * **类型安全 (Prisma):** Prisma的Schema优先方法，能根据数据库结构**自动生成完全类型安全的客户端**。这是我们端到端类型安全链条中至关重要的一环。
* **我们接受的权衡:**
    * **ORM的抽象层:** Prisma虽然强大，但它是一层抽象。在处理极其复杂的、需要手写SQL进行性能优化的查询时，可能会引入一些限制或需要“绕过”ORM。
* **缓解策略:**
    * 我们的原则是“**80/20法则**”：对于80%的标准CRUD操作，完全依赖Prisma的类型安全优势。对于20%的性能瓶颈查询，我们将使用Prisma的**原生SQL查询 (raw query)** 功能，并在代码中清晰地注释其原因。

## C. 前端 (Frontend)

### **Next.js (App Router)**

* **核心考量:**
    * **性能与用户体验:** 服务器组件(RSC)能显著减少发送到客户端的JavaScript代码量，加快初始加载和交互速度，这对于我们的“认知无障碍”目标至关重要。
    * **现代React特性:** App Router是React生态的未来方向，拥抱它可以让我们享受到最新的性能优化和开发模式。
* **我们接受的权衡:**
    * **范式转变:** App Router和服务器组件的思维模式与传统的客户端渲染(CSR)React有很大不同。团队需要时间来适应“客户端组件” vs “服务器组件”的心智模型。
    * **生态系统成熟度:** 围绕App Router的生态系统（例如某些状态管理库的集成）仍在快速发展中，可能会遇到一些边缘情况。
* **缓解策略:**
    * 我们将明确定义**何时使用服务器组件**（默认，用于获取数据和静态展示）和**何时使用客户端组件**（用于交互和状态管理），并形成文档化的最佳实践。

### **Zustand (State Management)**

* **核心考量:**
    * **极简主义与低认知负荷:** API极其简单，几乎没有模板代码，完美契合我们的核心哲学。
* **我们接受的权衡:**
    * **“魔法”般的简洁:** Zustand的简洁性背后是一些React Context和闭包的巧妙运用。它不如Redux那样有严格的、可追溯的数据流（Action -> Middleware -> Reducer），这在调试极其复杂的状态交互时可能稍显困难。
* **缓解策略:**
    * 我们将使用Zustand的**devtools middleware**，将其状态变化集成到Redux DevTools中，以增强调试能力。
    * 我们将制定严格的规范：**只在Zustand中存储真正必要的“全局状态”**，避免将其变成一个无所不包的“垃圾桶”。

### **Radix UI + Tailwind CSS**

* **核心考量:**
    * **无障碍与设计自由的完美结合:** Radix保证了底层无障碍，Tailwind提供了快速、一致地实现任何视觉设计的能力。
* **我们接受的权衡:**
    * **没有“开箱即用”的组件:** 与MUI或Ant Design不同，我们团队需要**自己组合Radix原语和Tailwind类名，来构建我们自己的Button、Modal等组件**。这需要更多初始的开发投入。
    * **HTML的“类名臃肿”:** Tailwind的原子化方法会导致HTML模板中出现大量的类名，这需要开发者适应。
* **缓解策略:**
    * 我们将投入资源，在`packages/ui`中构建一个**高质量的、可复用的内部UI组件库**。这是项目初期的核心任务之一。
    * 我们将使用Tailwind的`@apply`指令或组件封装来处理重复的类名组合，并利用Prettier插件自动排序类名，以保持代码的可读性。

## D. 部署 (Deployment)

### **AWS**

* **核心考量:**
    * **可扩展性、可靠性与生态系统:** AWS提供了最成熟、最全面的云服务，能够支持我们从初创阶段到大规模运营的整个生命周期。
* **我们接受的权衡:**
    * **复杂性与成本:** AWS的强大功能伴随着其固有的复杂性。相比于Vercel（用于前端）或Heroku等PaaS平台，直接使用AWS需要更多的DevOps知识。成本也需要被精细地监控。
* **缓解策略:**
    * **前端部署:** 尽管我们的后端在AWS上，但我们会将**Next.js前端部署在Vercel**上。Vercel与Next.js是同一家公司，其为Next.js提供的CI/CD、预览部署和全球CDN是无与伦比的，能极大地简化前端的DevOps工作。
    * **后端基础设施即代码 (IaC):** 我们将严格使用**AWS CDK**或**Terraform**来管理所有后端基础设施。**禁止任何手动的、“点击式”的控制台操作**，以确保环境的可复现性和一致性。
